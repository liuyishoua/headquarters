# 工作台业务任务架构：可行性与最小改动

## 结论与当前状态

**可以做，并且大部分平台操作应复用工作台现有实现。** 指挥中心作为目标
中枢，只向对应工作台提交业务任务；账号、平台规则、素材、联系对象和真实
写入由工作台负责。需要 agent 的任务由工作台调用既有 Channel→Multica
链路，模型结果返回工作台；业务完成后工作台返回可核验结果。直接读取由
工作台完成，不为每次读取创建 agent 任务。

此次仅核验与提出方案，**尚未按新边界迁移已部署的总部直接 Channel 动作
路径或总部原生模型规划路径**。新架构的业务执行应统一走工作台入口，不把
直接 Channel、直接 Multica 和工作台 API 混成三个可任选的业务执行入口。
总部自身规划属于目标控制循环，和派发账号业务任务需要明确区分。

不需要改 Multica 核心。工作台业务任务接口是受认证的内部接口，不要求新开
公网端口，也不需要把账号管理、登录资料、监听开关、所有底层平台 API 都
暴露给目标规划器。

## 一个统一业务接口，复用原有业务服务

每个工作台只补一层小的受认证业务门面，推荐提供以下契约。它们是建议，
当前两工作台尚无这些统一端点，不是现有已可调用接口。

- **能力目录**：返回本调用者可用的账号、业务操作、参数要求、读取来源、
  是否需要模型、是否产生平台写入、当前可用性/原因与结果类型。操作必须
  来自工作台真实实现，不能由模型或总部自行声明已有能力。
- **创建业务任务**：明确 operation、account、输入、稳定 request ID、目标/
  项目/主任务关联，以及受校验的授权引用。先持久化，再调用现有业务服务。
  同一 ID 和同一请求返回原任务；同一 ID 换输入拒绝，不重复执行。
- **查询任务/结果**：持久业务 task ID 与统一状态，如 queued、running、
  waiting_model、waiting_platform、succeeded、failed、uncertain、cancelled。
  提供结构化结果、真实来源、时间、覆盖范围与平台对象/回执引用。工作台
  自己的 job、ledger 条目、Channel事件、Multica任务作为可追踪关联保留。
- **查询事件与确认消费**：事务 outbox/递增游标回传任务结果或相关新观察；
  总部持久去重后唤醒目标。第一版可认证轮询，不一定先建设 webhook。若用
  回调，目的地固定且受认证，不能让模型填任意 URL。
- **撤回/取消**：总部暂停或撤权后，工作台再次检查待执行任务；已认领或
  已发出的平台写入保留待核对结果，不冒称撤销成功。

工作台执行时验证服务调用者、账号所有权、操作权限、具体资源/会话/联系
对象范围及授权版本/期限，再与真实能力交集执行。授权不能只是 prompt。
只读任务可直接产生持久 completed 结果，不需要额外代理或多次模型调用。
对外状态与结果不包含 cookie、来源令牌、内部报错或不相关私人聊天。

## 需要补齐的稳定性，不能直接包装按钮就声称完成

1. **统一关联尚缺。** 两平台现有 job/消息/ledger 没有完整、强约束的总部
   goal/project/task 关系。必须由工作台的任务关联表记录，不能只把字符串
   写进模型上下文。业务状态与平台证据由工作台产生，总部只验证并使用。
2. **闲鱼已有 request ID 去重，但没有全请求指纹冲突检查。** 当前同账号同
   ID直接返回原 job；新增门面须验证 operation/account/input/授权边界，
   防止同 ID 换动作误取旧结果。服务重启把未完成 job 标 unknown，而非自动
   恢复线程。安全读取可以重新排队；未知写必须先核对，不能盲重发。
3. **小红书发布需要特别处理未知写。** 通用 publish API 目前捕获异常标
   failed，其 retry API允许 failed 重试。超时可能发生在平台已经接受后，
   新门面不能把这类异常当可自动重试失败。应持久 intent、区分明确拒绝与
   uncertain、按发布键/账号/时间核对。现有 content_automation 与 DM
   ledger 中已有这类保护可复用，避免弱化为直接调用后不停 retry。
4. **回传需要 durable outbox。** HTTP返回丢失、总部重启、重复事件都不能
   丢业务结果或多次触发相同写动作。模型已返回、平台已提交、可见性已核验
   及业务目标已成交是不同状态，必须分别表达。

## 保留 Channel 留痕与 Multica 项目，无需改核心

需要模型的业务任务沿工作台→Channel→Multica→Channel→工作台运行；现有
Channel消息幂等、模型事件/状态与 Multica task/issue 留痕可以保留。无需
Channel承担全部平台业务 job，也不需要把它扩为通用任务调度系统。

但目前 Channel `multica.py:72` 从 **route.project_id** 关联原生 issue，
它不是每次业务任务的动态项目字段。把 project ID放进 context 只会提供
上下文，不会自动关联项目。要满足每个目标全部模型任务属于对应 Project，
应给既有工作台/Channel桥接补一个受服务端验证的关联字段或绑定机制，沿
原有正常 Multica API创建/更新任务的 project/parent 关系。必要时先把模型
任务引用写回项目主任务作为留痕，但引用不等于原生父子/项目归属；两者须
在界面和验收里区分。此为有限的桥接修改，不是 Multica 核心二次开发。

## 建议实施顺序与验收

先完成两平台共同业务门面及只读任务，证明账号隔离、关联和结果事件能持续
回总部；再复用既有工作台创作与回复执行流程接入异步业务任务。总部移除
账号业务动作的混合下发路径，只通过工作台契约执行；Channel原有模型链路
继续使用。最后逐项接已有真实发布/留言/会话创建，缺失能力单独补，不一次
大规模改全部平台。

每一步先用临时账号/合成平台验证 request ID重试、未知写、重启恢复、撤回
与目标关联。真实平台写必须另有明确的本次业务范围，不能用合成测试通过
来宣称已联系真实买家。最终现实验收仍看买家意愿、谈妥条件和可核验交付，
而不是模型完成数。

本轮可行性核验结束；未修改生产路由、任务执行器或平台开关。
