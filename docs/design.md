# 从消息工具到业务指挥部

## 业务锚点与责任

平台账号和 Channel 都是资源；用户管理的是目标。例如“完成商品咨询并确认客户需求”，而不是“运行某个账号的轮询”。一个目标可以横跨多个账号和平台，阶段可以使用不同 agent，结果仍记在同一个业务目标下。

| 组件 | 拥有的状态 | 主要职责 |
| --- | --- | --- |
| 指挥部 | 目标、阶段、账号资源、分工、期望指令、业务结果、验收记录 | 决定做什么、由谁做、何时停止，判断是否有证据达到标准 |
| Channel | 业务事件、会话事项、模型任务、动作、执行器租约、平台回执 | 接收事件、维护上下文、调用指定 agent、交付动作并追踪结果 |
| Multica | 指派给 agent 的任务单、追加评论、模型执行 | 理解上下文并提出下一步方案 |
| 工作台与执行器 | 平台登录、账号连接、实际读取与发送 | 观察平台、执行授权动作、返回真实平台标识 |

指挥部不持有平台 Cookie，不直接操作社交平台，不把普通模型文本解释为可执行指令。Channel 的机器控制接口不接受工作台来源凭据或浏览器会话。

## 目标、阶段和账号分工

目标包含整体诉求、共享业务知识、沟通风格和有序阶段。阶段包含具体要求和验收标准。每个账号分工绑定一个阶段、一个执行账号、一个 agent、业务入口、允许动作、沟通要求和审核模式。

示例：

1. “解决咨询”阶段，闲鱼账号 A 和另一平台账号 B 分别交给客服 agent。完成标准为两个明确业务对象的咨询已解决。
2. “确认跟进”阶段，指定账号与跟进 agent 继续工作。agent 得到前阶段已核实结果的摘要，具体私信仍只发给该平台事件绑定的会话。
3. 用户核实业务结果，验收最后阶段，指挥部撤回所有执行规则。

阶段按顺序推进。本版保留显式验收和下一阶段启动；阶段完成不会自动让另一个 agent 向真实用户发消息。不同阶段拥有独立执行规则和 Multica 会话绑定，避免不同 agent 复用旧任务时继续采用过期指令。

## 多目标争用与账号共享

账号资源以平台来源和稳定平台账号标识确定。同一平台账号在指挥部只登记一次，选择一个 Channel 执行。Channel 还会限制同一账号只能有一个在线执行器。

同账号可以承担不同目标，但两个运行目标不能同时接管重叠事件类型。启动时事务检查所有已运行目标、同一阶段分工，以及 Channel 原有本地规则。发生冲突时明确列出冲突目标，用户先暂停或调整分工。这里没有隐式抢占，也不让 agent 自己争夺账号。

每日额度、动作间隔、工作时间由账号统一配置，投影到所有相关执行规则。Channel 执行领取时按账号共享账本和最严格启用规则检查额度，同账号动作串行；待核对的动作阻止继续领取。

## 持久指令与授权

每个分工具有稳定的 UUID 执行规则标识。指挥部先在自己的数据库保存期望状态和递增版本，再下发 Channel。Channel 在事务中保存规则与指挥归属：

- 相同版本和相同内容幂等，仅更新授权期限；不同内容返回冲突。
- 旧版本不能覆盖新版本，因此晚到的旧“启用”不能越过新“暂停”。
- 指挥部不能接管原本不归属它的规则，Channel 管理页不能改写指挥部拥有的规则。
- 规则有效期为 90 秒，约每 25 秒批量续约；一次最多 500 条。续约不增加规则版本，因此不会反复撤销待执行动作。
- 暂停生成更高版本的禁用指令，撤销未领取动作和跟进计时器。已领取动作继续以平台真实回执为准。
- 暂停不能即时跨越断网生效；界面区分“期望暂停”和“下层已确认停用”。断网时旧授权最多 90 秒后不能再领取动作；已领取动作仍可能完成。

阶段切换先生成所有旧规则的撤回指令。相关阶段或同一账号的撤回未确认前，新分工不能获得授权。各 Channel 各自同步、下发和续约，某个 Channel 不可达不会卡住其他 Channel 的后台线程。

本版不提供跨 Channel 原子启动。多账号启动期间可能部分下发成功、部分等待；每项分工保留具体确认状态。要求绝对同时启动的业务需要后续增加准备/提交屏障。

## 事件、任务单和业务身份

Channel 原有 `(source, account, event_id)` 去重继续有效。平台重发不会复制事件；相同 ID 内容不同会报冲突。私信和跟进使用平台稳定会话标识，一次事项的连续消息追加同一 Multica 任务；新消息使未执行旧方案失效。

指挥部授权到期时，仍保留已启用执行规则对应的入站事件及待处理事项，标记等待授权；不继续发起新模型任务或领取动作。恢复授权后，只处理仍符合目标版本和最新会话状态的事项。暂停期间没有匹配启用规则的事件保留为未分流记录，不自动重放历史私信。

跨平台身份不能按昵称、头像或相似文本自动合并。业务结果使用用户明确填写的稳定业务对象标识；同一对象在多个平台完成同类结果，只计一次。该标识目前用于业务结果归并，不代表已经实现跨平台联系人的自动识别、全局会话锁或自动接力联系。后续如增加联系人映射，应保存映射来源、确认人和撤销记录，再引入按业务对象锁定的唯一执行负责人。

## 结果与完成度

三类事实分别保存：

1. 模型方案：agent 建议回复、跟进、转人工或等待。它不增加业务完成度。
2. 平台执行：账号执行器返回平台消息/作品标识，Channel 保存为成功回执。此时可以增加“发送成功”类技术指标。
3. 业务结果：用户核实“咨询解决”“需求确认”“作品验收”等事实，并引用本阶段的成功动作回执与说明，才增加对应业务指标。

同一业务对象同类结果去重；同一动作或相同平台回执不能重复制造多个客户成果。收到平台回执不代表对方已读、同意或成交。存在执行中或待核对动作时，不能验收阶段。

验收记录保留当时的标准和数量。已有执行证据的目标不能重写其诉求和标准；可以暂停调整分工，或创建一个新目标。这样不会把旧结果挪作新目标的完成证据。

## 本版与后续演进

本版已形成独立目标控制层、资源分配、指令下发、执行追踪和结果验收闭环。生产接入一个 Channel；两个独立 Channel 的业务闭环已用临时 HTTP 服务和虚构账号验证。

后续按业务价值推进：平台持续监听和执行适配；明确联系人映射与事项负责人；总指挥 agent 提出可审核的计划；依赖图、期限和动态资源分配；规模增长后的数据库、消息流和租约调度性能测试。这些属于后续能力，不能因为有配置字段或管理入口就宣称已实现。
