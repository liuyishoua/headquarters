# 账号操作能力差距映射

## 核心结论

**账号已经存在，不需要重复建立。许多发布和回复能力也已经实现；主要缺口是
现有工作台执行流程没有接到指挥中心的统一动作执行层。** 不能把总部的
“不可用”解释为平台应用没有能力，也不能把现有工作台服务运行解释为总部
已经能安全调用它的全部写操作。

本轮只读核对到：Channel 的指挥动作协议已启用，但 `connectors=[]`，没有
登记的账号动作执行器；小红书独立内容发布/评论程序与两平台工作台服务均
运行。闲鱼可选私信连接器代码存在，但它的运行配置文件不存在。本轮没有
改开关、注册连接器、发布内容、发消息或修改商品。

分类：① 工作台已有真实实现，总部未接入；② 对应桥接代码已有，但未配置
或未在线登记；③ 该受支持业务入口仅演示或未实现；④ 真实账号会话、权限、
素材或目标条件仍需核验。同一项可以同时属于①与④。

## 为什么总部显示不可用

`headquarters/capabilities.py:80` 起读取真实 Channel catalog，写操作仅在以下
条件同时满足时可用：支持 direct goal actions、source/account 精确匹配、
账号 connector 仍在线、connector 明确声明该 operation。当前 catalog
协议支持为真，但 connector 列表为空，所以没有可授权的真实写能力。

Channel `automation.py:290` 按 source+account 登记 heartbeat；`:303` 用最近
120 秒判断在线。`headquarters/channel_executor.py:35` 再核对账号、能力、
目标 grant、期限与具体对象；它的写白名单目前仅包含回复私信、回复评论和
发布作品。商品发布、商品修改、主动会话创建不能因为工作台存在类似 API
就自动通过这个白名单。

小红书与闲鱼现有 `/channel/messages` 或模型任务调用主要用于**把输入送给
agent 生成内容/回复**。这与总部新增的“账号动作认领→真实执行→认证回执”
协议不是同一条链路；已有模型绑定不会自动补齐执行桥接。

## 后续顺序

1. 复用现有账号与合法会话，不让用户重新建立账号。
2. 优先接已有真实只读搜索/刷新，再桥接既有回复与发布执行流程；账号和
   操作逐项核验、正确登记真实能力，保留原有去重、账号锁和未知结果核对。
3. 对仅演示/未实现项建立真实业务适配，不能凭提示词、skill 或开关充当实现。
4. 能力接通并明确商品条件后，再验证真实获客、对话、议价与用户交付；
   当前卖游泳卡目标仍未达成，文档验收不替代业务验收。

这里只做差距调查，未擅自启用真实社交写入或修改服务开关。
